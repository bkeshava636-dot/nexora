Based on the completed Nexora Feature Audit, implement ALL missing and partially implemented functionality.

IMPORTANT:

* Do not redesign the existing Nexora UI unnecessarily.

## PHASE 1 — Dynamic Academic Structure

Implement complete management for:

### Branches

Admin must be able to:

* Add branch
* Edit branch
* Delete branch
* Enable/disable branch
* Reorder branches
* Set branch name
* Set branch short name
* Set branch description

### Years

Admin must be able to:

* Add year
* Edit year
* Delete year
* Reorder years
* Associate year with a branch

### Semesters

Admin must be able to:

* Add semester
* Edit semester
* Delete semester
* Reorder semesters
* Associate semester with the correct year

### Subjects

Admin must be able to:

* Add subject
* Edit subject
* Delete subject
* Set subject name
* Set subject description
* Associate subject with the correct semester

The complete hierarchy must be:

Branch → Year → Semester → Subject → Resource

Do NOT hardcode branches, years, semesters, subjects, or resources.

The admin should be able to create a completely new branch without modifying source code.

## PHASE 4 — Complete Approval Workflow

Implement the actual workflow:

Student submission
→ Pending
→ Under Review
→ Admin approval
→ Published resource
→ Verified

When an admin approves a submission:

1. Change submission status to approved.
2. Create a corresponding public resource.
3. Preserve branch/year/semester/subject/resource type/title/description/Google Drive URL.
4. Mark the resulting resource as verified.
5. Record reviewed_at.
6. Record reviewed_by.
7. Make the resource visible in the student resource library.

When rejected:

1. Change status to rejected.
2. Store rejection reason.
3. Store reviewed_at.
4. Store reviewed_by.
5. Do NOT create a public resource.

The approved material MUST appear in the public resource library.

## PHASE 11 — Security / RLS

Implement proper Row Level Security.

Public students:

* Can read published resources
* Can read active branches/years/semesters/subjects
* Can submit materials according to the submission policy

Admins:

* Can manage academic structure
* Can manage resources
* Can review submissions
* Can approve/reject
* Can verify resources

Pending and rejected submissions must not be publicly readable.

Admin-only operations must be protected server-side/database-side, not just hidden in the UI.

Never expose a Supabase service-role key in frontend code.
