# NEXORA — College Academic Resource Platform

Build a modern, fast, responsive academic resource platform called **Nexora** for engineering students.

**Tagline:** Your Next Academic Resource Hub

Nexora should be a centralized platform where students can discover and access:

* Notes
* Previous Year Question Papers (PYQs)
* Question Banks
* Model Question Papers
* Important Questions
* Lab Manuals
* Lab Programs
* Assignments
* Study Materials
* Other academic resources

The platform must support multiple engineering branches, all 4 years, and all 8 semesters.

---

# 1. CORE ACADEMIC STRUCTURE

The most important hierarchy of Nexora is:

```text
Branch
   ↓
Year
   ↓
Semester
   ↓
Subject
   ↓
Resource
```

Example:

```text
Computer Science and Engineering (CSE)
        ↓
    2nd Year
        ↓
   3rd Semester
        ↓
 Data Structures
        ↓
      PYQs
```

Do NOT hardcode this structure into the frontend.

Everything must be dynamically managed through the database/admin panel.

# 4. STORAGE ARCHITECTURE

## Google Drive = Actual File Storage

Google Drive will store the actual academic files:

* PDFs
* Notes
* PYQs
* Question Banks
* Lab Manuals
* Assignments
* Other documents

**Do NOT store academic PDFs in Supabase Storage.**

The website should store only the Google Drive URL.

Example:

```text
https://drive.google.com/...
```

When students click **Open PDF**, open the Google Drive file.

Do not download or duplicate PDFs onto the website.

## Supabase = Metadata Database

Supabase PostgreSQL stores:

* Branch
* Year
* Semester
* Subject
* Resource title
* Resource type
* Description
* Google Drive URL
* Verification status
* New status
* Featured status
* Dates
* Submission information

# 25. AUTHENTICATION & SECURITY

Students should be able to browse resources without logging in.

Admin dashboard must require authentication.

Use Supabase Auth.

Only authorized admins can:

* Create resources
* Edit resources
* Delete resources
* Add/edit/delete subjects
* Manage academic structure
* Approve submissions
* Reject submissions
* Mark resources verified

Students can only create submissions.

Never expose the Supabase service-role key in frontend code.

Use environment variables.

Implement Row Level Security correctly.

Pending and rejected submissions must not be publicly accessible.

# 41. FINAL QUALITY REQUIREMENT

Nexora should NOT look like a basic CRUD application.

It should feel like a real modern education platform that engineering students would want to use regularly.

Prioritize:

**Speed + Simplicity + Organization + Trust + Mobile Experience**

The most important trust feature is the:

> ✓ Verified

badge, indicating that the Nexora admin team has reviewed the material.

The most important architecture principle is:

> **Google Drive stores the files. Supabase stores the metadata. Nexora provides the interface.**

Start by inspecting the current project and implement the application **stage by stage**.

After every stage:

1. Run the application.
2. Test the implemented functionality.
3. Fix errors.
4. Verify existing functionality still works.
5. Continue only when the stage is stable.

Do not move forward while major errors remain unresolved.
